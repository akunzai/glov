# Troubleshooting glov

A restart destroys the evidence a bug report needs. Capture these before restarting anything:

```sh
glov vm status <vm>      # VM state, Guest Service state and build, shares
glov vm stats --json        # Mac memory pressure and swap; each VM's CPU, memory and disk from the Mac and the guest
tail -n 50 "$HOME/Library/Application Support/glov/glovd.log"                    # Mac
Get-Content -Tail 50 "$env:LOCALAPPDATA\glov\glovd.log"                 # Windows host
glov vm screenshot <vm> -o screen.png
```

Guest logs: Windows `C:\ProgramData\glov\guest-service.log`; Linux `glov exec <vm> -- journalctl -u glov-guest -n 50`, where a Guest Service that hung leaves a goroutine dump; a Linux VM's boot console in `<vm dir>/console.log`, and the boot before in `console.previous.log` (on a Windows host, `glov vm console <vm>`).

## Symptoms

| Symptom | Cause | Recovery |
| --- | --- | --- |
| `vm create --engine vz` fails: "glov-image not found next to ... or in .../bin" | glov was built or installed without its disk image helper, which converts the cloud image and checks Ubuntu's signature | Run `tools/build.sh`, then `glov host install`; Linux guests need nothing from Homebrew |
| `glov vm create` fails: "missing host tools for Windows VMs: ...", or `glov host install` prints `note: Windows VMs need ...` | One or more of QEMU, `qemu-img`, `swtpm` or `wimlib-imagex` are not installed on this Mac | Run the `brew install ...` command shown in the message (for example `brew install qemu swtpm wimlib`); Linux VMs (`--engine vz`) need none of them |
| Guest Service `unresponsive` | The guest is stalled. Under Mac memory pressure (VM memory sums near the Mac's RAM, swap nearly full) its memory is paged out and it stops answering, even to console keys | `glov vm stats` shows the Mac's pressure and each VM's compressed memory. Free Mac memory (quit idle VMs and runtimes) or lower the VM's memory, then stop and start that VM: the stall can outlast the pressure. `vm start` warns on stderr before this happens |
| `vm status` running, Guest Service `connecting` for minutes | Still booting, the Guest Service did not start, or a filesystem check aborted | Inspect the screenshot and Linux `console.log`; for `RUN fsck MANUALLY`, follow [Offline filesystem recovery](#offline-filesystem-recovery) |
| `glov ssh <vm>` on a VZ VM fails with `Guest Service does not relay SSH yet` | The VM's Guest Service predates SSH over vsock, or is still starting | `glov vm wait <vm> guest-ready`; if it persists, `glov vm guest update <vm>`. An isolated VM's session forwards nothing (`-L`, `-R`, `-A`, `-X` are undone); copy files with `glov cp` instead |
| In an isolated VM, `curl` fails with `CONNECT tunnel failed, response 403` (`apt` with `403 Forbidden`), or a tool reports connection refused | The egress policy refused it: the host is not in the allowlist, or it resolves only to a private or host (Mac or Windows) address. `glov egress log <vm> --denied` names the host, port and reason | Ask the user before widening the policy, then `glov egress allow <vm> <host>` (`*.suffix`, or `host:port` for a port other than 443/80); it applies to the next connection, no restart. A host on a private network or VPN (denied with `no public address`) needs the user to run `glov egress allow <vm> <host> --private`, and, for an internal CA, `glov vm trust add <vm> <ca.pem>`; MCP cannot do either. Never work around the proxy: the VM has no other route |
| In an isolated VM, a request fails at once with no response (`curl: (56) Recv failure: Connection reset by peer`, or exit code 000 from `-w %{http_code}`), and `glov egress log <vm>` shows it allowed with `(upstream reset)` | The host it reached, or the network on the way, reset the connection after the request. The proxy passed the reset on; the same request from the host without the proxy can fail the same way | Retry the request if it is safe to repeat. If it keeps happening, try the same request from the host (the Mac, or Windows) to tell a remote or network problem from a glov one |
| In an isolated VM, a tool fails with `Could not resolve host` or `Temporary failure in name resolution`, and `glov egress log <vm> --denied` shows nothing for it | The tool ignores `HTTPS_PROXY`/`HTTP_PROXY` (some clients do, as does `curl --noproxy` or an emptied environment). The VM has no DNS and no route, so such a client fails closed | Point the tool at the proxy: keep `HTTPS_PROXY=http://127.0.0.1:3128` (from `/etc/environment`) in its environment, or set its own proxy option. Allowing more hosts does not help: the policy never saw it |
| In an isolated VM, a host allowed with `--private` gets `CONNECT tunnel failed, response 502`, and `glov egress log <vm> --denied` says `unreachable; a host on the Mac's own LAN needs Local Network access for glovd`; or a private service's certificate is not trusted | macOS Local Network privacy blocks glovd (a launchd agent) from the Mac's own Wi-Fi and Ethernet networks until the user allows it; hosts through a VPN are not affected. An internal CA the VM was not given fails TLS like any unknown CA | Tell the user to allow glovd in the macOS alert that the first such connection brings up, or, if they denied it, to switch glovd on under System Settings > Privacy & Security > Local Network. For the CA, the user runs `glov vm trust add <vm> <ca.pem>` (one certificate per file; `glov vm trust list` shows what the VM has); MCP cannot add trust |
| In an isolated VM, a request to a host fails with a certificate error (`unable to get local issuer certificate`, `self-signed certificate in certificate chain`, `UNKNOWN_CA`), or answers 403/502 starting `glov egress proxy:` and naming a secret | That host is bound to a secret granted to the VM, so the proxy terminates TLS with the egress CA and substitutes `glov-secret:<name>`. A certificate error means the client does not trust that CA: the VM predates the CA, or the program reads neither the system store nor `NODE_EXTRA_CA_CERTS`/`SSL_CERT_FILE`. A 403/502 names the secret and the fix (not granted, not bound to the host, unreadable value) | For a certificate error, check `glov egress log <vm>` for `guest TLS`; a VM made before the CA must be recreated, and a program with built-in roots needs its own CA option pointed at `/usr/local/share/ca-certificates/glov-egress-ca.crt`. For a 403/502, tell the user the message: granting or defining secrets is theirs to do |
| `glov vm balloon <vm>` refuses: "has no balloon device", "does not give the memory a balloon takes back to macOS", or "was started without its balloon device" | The VM predates the balloon setting or was created without glov-qemu installed; the QEMU is not glov-qemu (Homebrew's keeps that memory on macOS); or the VM was started before the setting or glov-qemu changed | Do what the message says: `glov vm stop`, `glov vm configure <vm> --balloon on`, `brew install akunzai/tap/glov-qemu`, then `glov vm start`. A live snapshot taken before the change is then refused on revert (see the `glov snapshot revert` row) |
| `glov vm balloon <vm> <size>` returns, but the guest keeps more than the size | The guest hands memory over gradually, and Windows stops early when it runs short | Check again with `glov vm balloon <vm>` after a minute; free memory in the guest or pick a larger size |
| `glov vm balloon <vm>` in auto says `no memory stats from the guest (is its balloon service running?)` | The guest is still booting, or its balloon service (`blnsvr.exe`) is not installed or not running: a Windows VM made before glov's setup installed it has the driver but not the service. Auto then leaves the target where it is | Wait a minute after boot. If it persists, take `Balloon/2k25/ARM64/blnsvr.exe` from the cached virtio-win ISO (`~/Library/Caches/glov/windows/virtio-win-*.iso`, or `$GLOV_CACHE/windows/`; `w11/ARM64` is a hard link to it that `bsdtar` does not extract), `glov cp` it to `<vm>:'C:\Program Files\glov\blnsvr.exe'`, and run `glov exec <vm> -- 'C:\Program Files\glov\blnsvr.exe' -i` (not through `cmd.exe /c`, which breaks the quoting) |
| In auto, the target stays at the VM's full memory, or does not go down right after the guest frees memory | Use plus headroom (2G or half of it while the Mac's memory pressure is normal) reaches the VM's size; or the last change was less than a minute ago (the reason says `going down to <size> in <n>s`) | Nothing to fix: the reason line under `glov vm balloon <vm>` says which. Under memory pressure the headroom shrinks to 1G; a fixed size (`glov vm balloon <vm> <size>`) overrides auto |
| `glov snapshot revert` refuses: `live snapshot "<name>" was taken on another machine than VM <vm> would start now (...)` | Since the snapshot, the balloon setting, the QEMU build (`glov-qemu` installed or removed, or upgraded), or CPUs or memory changed; QEMU cannot load it into a different machine | Run the fix the message names (`glov vm stop <vm>` first, then `glov vm configure <vm> --balloon on` or `off`, `--cpus`, `--memory`, or reinstall or remove `glov-qemu`) and revert again; or revert a disk-only snapshot with the VM stopped; or take a new live snapshot |
| `glov snapshot create` of a running harness VM fails with `was given tmpfs secrets since it booted`, or `glov secret grant`/`revoke`/`set`/`remove` answers `saved, but <vm>: cannot deliver tmpfs secrets` | The VM's harness holds a secret in `/run/glov/secrets`, and a live snapshot would save guest memory; or the Guest Service could not write or remove those files (too old, or not answering) | Stop the VM and take the snapshot then (disk-only, without the secret). For a failed delivery, the grant is saved and the next Guest Service session retries; after a revoke, stop the VM if the value must leave the guest at once, or `glov vm guest update` an old Guest Service |
| On a Mac, a request fails with 502 `glov egress proxy: ... Keychain: cannot read <name>` | The daemon was rebuilt or reinstalled and the Keychain item still trusts the old build | Tell the user to run `glov secret set <name> --host <host>` again (it replaces the item for the running daemon), or to choose Always Allow on the Keychain prompt |
| On a Windows host, any `glov` command fails with `glovd cannot start: unsafe data directory: <path> grants access to <SID>` | Something other than glov changed an ACL in the glov home (`%LOCALAPPDATA%\glov`), and glovd refuses to start on a folder another account could write to | Tell the user to look at `<path>` and, if it is theirs, run `glov host install` (non-elevated): it resets the ACLs. A path owned by another user is refused even then; the user inspects and removes it |
| `exec --as user` exits 75 (`Guest Service error 4: no user is signed in`) | No one is signed in to the console; a harness VM signs in by itself a few seconds after the Guest Service is ready | Sign in (`glov view <vm>`), or poll until a session exists |
| `share sync` prints nothing for minutes | Hashing, or blocked on a file a guest process holds open | `glov share status <vm> --watch` from another terminal: the file whose bytes stop growing is the culprit |
| `share sync` fails: "the guest is not listing, yet its listing never reached the host" | A message between host and guest was lost (cause unconfirmed); seen after hours of syncs under Mac memory pressure | Sync again; if it repeats, `glov vm reboot <vm>` |
| "a sync of share X is already running" after killing the client | The guest side outlived the client | Retry once; if it persists, `glov vm stop <vm> && glov vm start <vm>` |
| `guest update` refuses: jobs, sync or mount in progress | glov will not interrupt managed work | Wait, or `--force` (interrupts jobs, cancels a sync) |

A reboot or stop/start interrupts everything on that VM, including another agent's runs. Confirm nothing else is using it and announce the restart before running it. Every row that needed a restart or a workaround gets a bug report (see the main skill).

## Offline filesystem recovery

`RUN fsck MANUALLY`, `multiply-claimed blocks` or `Filesystem errors left uncorrected, aborting` on the Linux boot screen means filesystem errors have blocked normal startup. An empty `console.log` does not rule this out: inspect `glov vm screenshot <vm> -o screen.png`. Mask identifying information before sharing captures. The screen establishes the boot failure, not when or why the disk became damaged.

1. Stop the VM (`glov vm stop <vm>`). Proceed only after VM status is `stopped` and no process has its disk image open.
2. Back up the complete disk image while stopped. Verify the backup covers the exact image being repaired and retain it until application data has been checked.
3. Identify the filesystem partition from this image's partition table. Use its actual partition device or verified byte offset; offsets from another VM are not reusable. Run an offline read-only check (`e2fsck -fn <filesystem>`) and review its findings before choosing repairs.
4. Repair that filesystem offline with `e2fsck`, then repeat `e2fsck -fn <filesystem>` while it is still offline. Continue only when the check exits `0`; otherwise retain the backup and report the remaining errors.
5. Start the VM and verify readiness: `glov vm wait <vm> guest-ready --timeout <s>`. Check affected applications and data separately. Cloning multiply-claimed blocks restores separate allocation, not the original file contents.

[e2fsck's manual](https://github.com/tytso/e2fsprogs/blob/master/e2fsck/e2fsck.8.in) explains the recovery boundary: boot-time `-p` repairs only problems safe for unattended handling and leaves others for intervention. Keep that boundary; `-y` approves every repair and belongs only in a reviewed recovery with a verified backup. Run repairs with the filesystem unmounted.
